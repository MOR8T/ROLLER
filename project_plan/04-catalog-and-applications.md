# Этап 04 — Каталог, категории и применения

**Фаза:** 1 (Frontend) · **Зависит от:** 03

## Цель
Каталог профильных систем (без цен), страницы двух категорий по материалу и
SEO-лендинги применений.

## Предусловия
- i18n-каркас готов (этап 03) — все новые страницы сразу мультиязычные.
- В `data/` описаны категории, применения и товары с типами.

## Структура — две оси

Товар = **профильная система**. Организация:

- **Категория** = материал: `pvc`, `aluminium` (2 записи). Это «дом» товара и его URL.
- **Применение** = фасет + отдельный SEO-лендинг. Связь с товаром — многие-ко-многим.

Причина: одна система (ROLLER) идёт и на окна, и на двери — положить её
в категорию «пластиковые окна» нельзя. При этом SEO-запросы из брифа п.14.2
(«пластиковые окна Душанбе», «алюминиевые двери Душанбе», «фасадное остекление»)
надо отрабатывать — этим занимаются лендинги применений.

### Применения (первичный список)
`windows`, `doors`, `sliding-systems`, `facade-glazing`, `mosquito-nets`,
`partitions`. Список уточняется вместе с контентом.

**Реализовано ровно в этом составе.** У `mosquito-nets` систем нет — сетки
относятся к комплектующим, которые к запуску в каталог не заводим (см.
«Заметки»). Лендинг остаётся: он отрабатывает поисковый запрос, а вместо сетки
систем показывает пустое состояние «изготавливаем под размер» + CTA.

## Модель данных (мок = будущий контракт API)

```ts
type Locale = 'ru' | 'tg' | 'en' | 'tr';
type I18n = Partial<Record<Locale, string>>;   // фолбэка нет: нет значения → пусто

type Category = { slug: 'pvc' | 'aluminium'; title: I18n; description: I18n; image: string };

type Application = { slug: string; title: I18n; description: I18n; image: string };

type Spec = { name: I18n; value: I18n };        // гибкие пары, не фиксированные колонки

type Product = {
  slug: string;
  name: string;                                  // латиница, не переводится
  kind: 'system' | 'component';
  categorySlug: Category['slug'];
  applicationSlugs: string[];
  segment: 'economy' | 'standard' | 'upper' | 'premium';
  shortDescription: I18n;
  description: I18n;
  specs: Spec[];
  colors: string[];
  images: string[];
  logo: string | null;                           // у алюминиевых брендов — null
  popular: boolean;
};
```

> **Почему `specs` — список пар, а не фиксированные колонки.** У москитной сетки,
> подоконника или ручки нет ни камер, ни стеклопакета. Гибкая схема принимает
> любой товар без миграций и позволяет заказчику самому заводить комплектующие
> через админку. Фильтры по брифу нужны только по категории и сегменту, так что
> типизированные колонки ничего не дают.
>
> ⚠️ Для **конфигуратора** (этап 06) этих пар недостаточно — ему нужны
> машиночитаемые справочники. Это открытый вопрос №1 в `00-overview.md`.

## Проверка: что не сошлось с планом

### 1. Применения были не тем, чем их считала главная

Главная с этапа 02 показывала четыре **ситуации** — `apartment`, `house`,
`commercial`, `facade` — и вела ими на `/solutions/*`. `00-overview.md` §1 и
этот этап определяют `Application` иначе: `windows`, `doors`,
`sliding-systems`, `facade-glazing`, `mosquito-nets`, `partitions`.

Совместить нельзя, и дело не в списке слов. Применение обязано быть **фасетом
товара** (связь многие-ко-многим, фильтр в каталоге). Ситуация фасетом быть не
может: любая из шести систем подходит и для квартиры, и для частного дома —
связь получилась бы «все со всеми» и не несла бы информации. Плюс SEO-запросы
брифа п.14.2 сформулированы по изделию, а не по объекту.

**Сделано:** канонический список — из плана; секция «Применения» на главной,
мега-меню и мобильное меню переведены на него. Требование `DESIGN.md` §7
(«первый выбор — не материал») сохранено: «окна или фасад?» владелец квартиры
отвечает так же уверенно, как «квартира или дом?».

⚠️ **Это правка утверждённой главной** — меняются подписи четырёх карточек
(теперь шести) в секции «Применения». Вёрстка и композиция не тронуты.

### 2. Шесть систем лежали в двух местах

`brandLineup` в `data/home.ts` и товары каталога — это один и тот же набор из
шести систем. Держать две копии значит ровно ту рассинхронизацию, которую этап
03 уже вычистил из мега-меню (`catalogMenu` с комментарием «kept in sync»).

**Сделано:** единственный источник — `products` в `data/catalog.ts`. Секция
брендов на главной рендерит его же. Карточки при этом разные и такими остаются:
на главной — «какая из шести моя» (полоса характеристик + строка «для кого»), в
каталоге — «что это за система» (именованные пары `specs` + второй CTA).

### 3. Сегменты: код против наброска модели

Модель в этом файле называет сегменты `economy | standard | upper | premium`.
Код с этапа 01 использует `economy | mid | upper-mid | premium`, и на этих
ключах завязаны все четыре словаря. Взят код — то же решение, что план сам
принимает для `pvc` против `pvh`.

### 4. Текст `specs` живёт в словарях, а не в `data/`

План описывает `Spec = { name: I18n; value: I18n }`. В репозитории с этапа 03
действует правило: `data/` — только то, что одинаково во всех локалях, текст —
в `messages/*.json`. У пары «Глубина профиля / 60 мм» переводимы обе стороны,
locale-независимой половины нет вообще.

**Сделано:** пары целиком в словарях (`products.items.<slug>.specs`), читаются
через `t.raw()`. Контракт тот же — на бэкенде это JSONB-массив, — а гибкость
схемы даже выше: товар объявляет любой набор пар, вёрстка ничего не
предполагает. Карточка берёт первые три пары, не первые три *колонки*.

### 5. Фильтры не в URL

Фильтры каталога — локальное состояние клиентского компонента, а не
`searchParams`. Систем шесть, фильтрация мгновенна и грузить нечего; страницы,
которые имеет смысл шарить и индексировать, — это `/catalog/[category]` и
`/solutions/[application]`, у них свои тексты и метаданные.

### 6. FAQ-блока нет

План допускает его «при наличии контента» — контента нет. Придумывать за
заказчика ответы про гарантию и сроки хуже, чем отсутствующая секция.

### 7. Побочные находки

- Удалены `components/sections/products-section.tsx` и
  `components/sections/product-card.tsx` — они лежали с комментарием «kept for
  the catalog, stage 04»; каталог их заменил. `categories-section.tsx` разобран
  на переиспользуемый `CategoryCard`.
- CTA «Подобрать» на карточке ведёт на форму заявки в подвале той же страницы
  (`#lead-form`), а не на `/calculator` — конфигуратор появится на этапе 06, а
  до тех пор карточка не должна вести в 404.
- `RevealGroup` намеренно не оборачивает фильтруемую сетку: scroll-driven
  анимация оставляет карточку, смонтированную вне диапазона, на `opacity: 0`.
- Открытый вопрос №7 (`/showroom`) по-прежнему открыт.

## Заметки
- Цены не показываем — везде «Цена по расчёту» + CTA.
- Комплектующие (сетки, подоконники, кабель-каналы, шины, цилиндры) в каталог
  к запуску **не заводим** — контента по ним нет. Схема их принимает; заказчик
  добавит через админку, когда появятся фото и тексты.
