# Этап 13 — Интеграция frontend ↔ backend

**Фаза:** 3 (Интеграция) · **Зависит от:** 11, 12

## Цель
Заменить моковые данные фронтенда реальными данными из API.

## Предусловия
- Публичный API (этап 11) и админка (этап 12) работают.
- На фронтенде данные читаются через единый слой (`data/` + типы из этапа 04).

## Задачи
- [ ] `lib/api.ts` — типизированный клиент (базовый URL из окружения),
      прокидывает текущую локаль в `?lang=`.
- [ ] Заменить чтение из `data/` на запросы к API:
      каталог, категории, применения, товары, новости, портфолио, баннеры,
      контакты, справочники конфигуратора (если они в БД).
- [ ] **Изображения из API**: настроить `next.config.ts` `images.remotePatterns`.
      Все временные фотографии заменяются через админку — правок кода быть не должно.
- [ ] Подключить `submitLead()` к `POST /api/leads`.
      **Порядок строго: сохранение → затем открытие WhatsApp.** Интерфейс
      заложен на этапе 06, формы не переписываются.
- [ ] Стратегия рендеринга под каждую страницу (SSG / ISR / SSR).
      Каталог, товары, лендинги применений — **ISR** ради SEO и скорости.
      Учесть множитель: страниц × 4 локали.
- [ ] Ревалидация после правок в админке.
- [ ] Обработка состояний загрузки и ошибок на страницах — явно.
- [ ] `NEXT_PUBLIC_API_URL` и прочие переменные окружения фронтенда.
- [ ] Проверить локализацию данных из API на всех четырёх локалях, включая
      случай отсутствующего перевода: поле выводится **пустым**, страница не ломается.

## Результат / артефакты
- Сайт полностью работает на данных из БД; контент управляется через админку.

## Критерии готовности
- Все страницы отображают данные из API на четырёх локалях.
- Изменения в админке отражаются на сайте (с учётом ISR-ревалидации).
- Заявка сохраняется в БД **до** открытия WhatsApp; обе части проверены.
- Замена изображения через админку не требует деплоя.
- `build` / `lint` чистые.

## Заметки
- Контракт API и TS-типы должны совпадать — расхождения фиксировать в типах,
  а не «чинить» на лету в компонентах.
